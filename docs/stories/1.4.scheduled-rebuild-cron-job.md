    ```javascript
    app.post('/api/trigger-rebuild', async (c) => {
      const { GITHUB_TOKEN, GITHUB_OWNER, GITHUB_REPO, GITHUB_EVENT } = c.env;

      if (!GITHUB_TOKEN) {
        return c.json({ error: 'GitHub token not configured' }, 500);
      }

      try {
        const response = await fetch(
          `https://api.github.com/repos/${GITHUB_OWNER}/${GITHUB_REPO}/dispatches`,
          {
            method: 'POST',
            headers: {
              'Authorization': `Bearer ${GITHUB_TOKEN}`,
              'Accept': 'application/vnd.github+json',
              'Content-Type': 'application/json',
            },
            body: JSON.stringify({
              event_type: GITHUB_EVENT || 'rebuild-farms',
              client_payload: {
                reason: 'Manual trigger via API',
                triggered_at: new Date().toISOString(),
              },
            }),
          }
        );

        if (!response.ok) {
          throw new Error(`GitHub API error: ${response.status}`);
        }

        return c.json({
          success: true,
          message: 'Rebuild workflow triggered',
          repository: `${GITHUB_OWNER}/${GITHUB_REPO}`,
          event_type: GITHUB_EVENT || 'rebuild-farms',
        });
      } catch (error) {
        console.error('Failed to trigger rebuild:', error);
        return c.json({ error: 'Failed to trigger rebuild workflow' }, 500);
      }
    });
    ```

### Technical Constraints

**GitHub Actions Cron Limitations**:
- **Cron Precision**: GitHub Actions cron is not precise (can be delayed by 3-10 minutes)
- **Concurrency**: Only 1 cron workflow runs at a time (subsequent runs queued)
- **Timezone**: All cron schedules use UTC time (not local time)
- **Frequency**: Minimum interval is every 5 minutes (more frequent not recommended)

**Cloudflare Pages Deployment**:
- **Deployment Time**: ~3-5 minutes for typical PickAFarm build
- **Build Concurrency**: 1 concurrent build per project (queued if multiple triggered)
- **Cache Invalidation**: CDN cache invalidated automatically on new deployment
- **Rollback**: Previous deployments retained (can rollback via dashboard)

**D1 Database Access from GitHub Actions**:
- **Authentication**: Requires Cloudflare API token with D1 read permissions
- **Rate Limits**: Cloudflare API has rate limits (~1200 requests/5 minutes)
- **Read-Only Recommended**: Use read-only token for security (prebuild scripts only read)
- **Connection**: Access via D1 REST API (HTTP POST with SQL query)

**WordPress API Access**:
- **Availability**: WordPress may be unreachable (hosting downtime, network issues)
- **Fallback**: Prebuild scripts should handle WordPress downtime gracefully
- **Rate Limits**: WordPress REST API typically has no rate limits (but may have hosting limits)
- **Timeout**: Set reasonable timeout (30-60 seconds) to avoid workflow hanging

[Source: docs/architecture/architecture.md#technical-debt, GitHub Actions documentation]

### Security Considerations

**GitHub Secrets Management**:
- **Cloudflare Tokens**: Use least-privilege tokens (Pages deploy + D1 read only)
- **Slack Webhook**: Webhook URL is sensitive (leaking allows spam to Slack channel)
- **GitHub Token**: Automatically provided by GitHub Actions (`secrets.GITHUB_TOKEN`)
- **Rotation**: Rotate all tokens every 90 days (document rotation schedule)

**Worker API Security**:
- **`/api/trigger-rebuild` endpoint**: Currently has no authentication (public endpoint)
  - ⚠️ **Risk**: Anyone can trigger rebuild (potential abuse)
  - **Mitigation Options**:
    1. Add simple token in query parameter: `?token={secret}`
    2. Rate limit endpoint (Cloudflare Worker rate limiting)
    3. IP whitelist (GitHub Actions IP ranges)
  - **Recommendation**: Start with option 1 (token parameter) for simplicity

**Environment Isolation**:
- Scheduled rebuilds use production environment variables
- Same as webhook-triggered rebuilds (no isolation needed)
- Read-only D1 access prevents accidental data modification

[Source: docs/architecture/architecture.md#authentication--user-management]

### Cron Schedule Strategy

**Why Every 2 Hours?**:
- **Data Freshness Balance**: Frequent enough for farmer updates, not too aggressive
- **Build Cost**: Cloudflare Pages has build minute limits (free tier: 500 minutes/month)
- **Resource Usage**: Fewer builds = less GitHub Actions minutes, less D1 queries
- **User Expectation**: Farmers expect updates within 2-3 hours, not real-time

**Alternative Schedules**:
```yaml
# Option 1: Every 2 hours (RECOMMENDED)
cron: '0 */2 * * *'           # 12 builds/day = ~360 builds/month

# Option 2: Every 4 hours (CONSERVATIVE)
cron: '0 */4 * * *'           # 6 builds/day = ~180 builds/month

# Option 3: Business hours only (8 AM - 8 PM UTC)
cron: '0 8-20/2 * * *'        # 7 builds/day = ~210 builds/month

# Option 4: Peak hours (more frequent during day)
# Morning: 0 6,8,10,12 * * *
# Afternoon: 0 14,16,18,20 * * *
# Total: 8 builds/day = ~240 builds/month
```

**Recommendation**: Start with every 2 hours (`0 */2 * * *`). Monitor resource usage and adjust if needed.
